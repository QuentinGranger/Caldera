# Audit de sécurité — 5 octobre 2026

Périmètre : code Next.js, Server Actions, routes API, authentification admin et client, commandes, Stripe, imports, images, configuration HTTP, dépendances et fichiers suivis par Git. Les essais initiaux ont utilisé un build de production et la base PostgreSQL QA locale `caldera_qa_20261004`. Le 6 octobre, la CI et le domaine public ont été revérifiés après déploiement ; les services Stripe, Resend et Blob réels n'ont pas fait l'objet d'une transaction de bout en bout.

## Contrôles sans faille exploitable trouvée

- Les opérations admin examinées imposent une session serveur et un rôle `ADMIN` actif. Les tests HTTP refusent l'accès anonyme, le cookie client et les appels Server Actions d'origine étrangère.
- Les cookies d'authentification sont `HttpOnly`, `Secure` en production et révoqués à la déconnexion ; les pages privées répondent sans cache partagé.
- Les webhooks vérifient la signature Stripe. Les opérations de paiement relisent Stripe, contrôlent le mode, le montant, la devise, les métadonnées et l'idempotence avant les changements de commande ou de stock.
- Les requêtes SQL dynamiques d'import contrôlées dans cet audit passent leurs données comme paramètres. Les images sont limitées, décodées puis réencodées en WebP ; les médias sont servis via un chemin UUID contrôlé.
- Aucun bypass de maintenance n'a été détecté dans le code suivi par Git. La recherche de motifs de secrets connus n'a rien trouvé dans les fichiers suivis ni dans les ajouts de l'historique Git. Les variables `NEXT_PUBLIC_*` observées concernent la clé Stripe publiable, le DSN Sentry et l'environnement Vercel.
- Le contrôle HTTP n'a trouvé aucun en-tête CORS autorisant une origine tierce sur `/api/contact`.

## Vérification

- `npm run build`, `npm run typecheck`, `npm run lint` et `git diff --check` : réussis.
- Tests de monitoring, contact, limites PostgreSQL, autorisation admin, paiements, réinitialisation, comptes, administration et import fournisseur : réussis.
- Sur le serveur de production local : en-têtes présents sur HTML, API et image statique ; préflight d'origine tierce sans autorisation CORS ; webhook surdimensionné rejeté avec `413`.
- `npm audit --omit=dev` : aucune vulnérabilité signalée après mise à jour.

## Actions et risques restants

1. **Déploiement effectué** : le commit `ecab17f` est servi en production. Le catalogue reste masqué avec `caldera_preview=1` sur le domaine principal et l'alias Vercel. Les en-têtes HTTPS/HSTS et les refus des requêtes anonymes testées ont été confirmés. Vérifier encore dans les tableaux de bord les secrets de production, la correspondance des clés Stripe, la réception d'événements webhook et les tâches cron. Aucun secret exposé n'a été identifié dans le dépôt ; aucune rotation n'est déduite de cet audit.
2. **Dépendance de développement** : `npm audit` complet signale encore 5 alertes élevées liées à `braces` via `eslint-config-next`. `braces` n'a pas de version corrigée publiée à cette date ; la chaîne est absente de l'audit des dépendances de production. Surveiller la publication d'un correctif et mettre à jour sans rétrograder Next.js.
3. **Abus de stock** : un visiteur peut créer plusieurs paniers et réservations temporaires. Ajouter une règle de limitation WAF/edge fondée sur une IP de confiance et surveiller les réservations annulées ; le code ne dispose pas d'une identité réseau fiable pour fixer une limite IP sans risque de contournement.
4. **Administration** : une MFA admin renforcerait la protection contre le vol d'identifiants ; son ajout exige un parcours de configuration et de récupération à définir.
5. **Services externes** : aucun envoi réel Resend, aucun upload Vercel Blob réel et aucun webhook de l'environnement Stripe déployé n'ont été exécutés pendant cet audit.

Les tests et la recherche de motifs ne prouvent pas l'absence de toute vulnérabilité ; un test d'intrusion du déploiement reste utile avant ouverture de la boutique.
